# Automatic draft recovery

Unsaved business forms automatically keep an encrypted recovery copy in the current browser tab. After reload, navigation back, or sign-in, an available copy offers **Restore draft** and **Discard draft**. Restoring is an explicit choice and never submits a form. If the current form already has changes, replacing them requires confirmation.

Supported forms are new lists, list details, new items, item edits, public profiles, share-link expiration options, and viewer purchase quantities. Search filters, authentication forms, passwords, upload/file inputs, hidden antiforgery fields, and read-only share addresses are excluded.

## Storage and identity

The web host implements the shared `IDraftRecoveryStore` interface using ASP.NET Core Data Protection and `sessionStorage`. Values are encrypted and authenticated on the server before storage. Protection purposes bind them to the validated account/tenant identity and the specific form/list context. Browser keys contain hashes rather than account identifiers or private list names. Browser records contain ciphertext and an expiration timestamp; the authoritative expiry is also inside the protected payload and is checked using the server clock. Changing browser metadata cannot extend it.

Drafts expire 24 hours after preservation. There are at most 32 entries per account/anonymous namespace in a tab, with a 64 KiB plaintext payload limit per entry and at most 32 captured fields. Expired or unreadable entries are removed on access; writes also prune expired entries in that namespace. There is no background browser cleanup when the app is not running, so expiry prevents recovery rather than promising physical deletion at exactly 24 hours. Storage/key failures show a generic fallback and never log draft contents.

An account change cannot rebind an old circuit's data to the new account. Other accounts, other tenants, anonymous users, and Admin callers do not acquire access to the account's recovery copy. The session-change guard still blocks authenticated API work from a stale circuit, and restoration waits for a fresh signed-in page. Losing access to a list does not grant access through a draft: list/item editors are offered only after the ordinary authorized reads succeed, and restored item IDs must still exist in the current list.

Anonymous recovery is limited to viewer quantities. Its random tab namespace is separate from account drafts and does not authorize list access. An authorized viewer who signs in in the same tab may explicitly recover that anonymous quantity; saving the account-bound copy removes the anonymous copy for that form. This does not transfer purchase ownership or bypass the existing share/guest credential checks.

Browser storage is a convenience, not a backup or a cross-device sync service. Session storage survives reloads and page-session restores; browsers may initially copy it into a tab opened by another tab, after which the copies are independent. Closing or clearing the page session can remove it. See [MDN's session storage documentation](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage). Copies remain subject to account/context protection and server-checked expiry. The underlying [ASP.NET Core Data Protection](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/introduction?view=aspnetcore-10.0) key ring must remain available; existing key-retention rules still apply.

## Save and restore behavior

- Input/change events capture raw editable fields, including text that has not blurred and temporarily invalid numeric input. A 400 ms debounce saves a typed model plus those raw values. This retains concurrency metadata while allowing the UI to reproduce incomplete input without submitting it.
- The UI distinguishes **Saving recovery draft…** from a confirmed saved copy. An older completion cannot mark newer pending edits as saved. Navigation/sign-in recovery flushes pending copies with a two-second wait budget; browser termination, a broken connection, blocked storage, or leaving before confirmation can still lose the latest input. Existing unload/navigation warnings remain active.
- Restoring applies the typed model and raw field values to the correct form, marks the form unsaved, and asks the user to review/save. Original row versions are retained. A concurrent list/profile/item change therefore still requires the normal conflict-resolution flow; recovery cannot silently overwrite it. An immutable profile handle stays aligned with the saved profile.
- Purchase drafts retain their original idempotency key and attempted flag. Before sending a mark, a checkpoint records that attempt. Recovery never sends the request automatically or replaces its key. Retrying after a committed mark's response was lost returns the same mark. A changed actor/quantity still encounters the existing conflict checks rather than creating an implicit replacement.
- Successful writes and explicit editor cancellation clear the corresponding recovery copy. Failed writes retain it. Clear/reset epochs reject delayed callbacks so an old autosave cannot resurrect a cleared draft. Discarding an offered copy does not submit or archive anything.
- An unavailable/archived item cannot be restored into another item's editor. Read-only fields, passwords, file inputs, hidden values, and fields outside the target form are never replayed. Unreadable or unsupported snapshots are discarded safely.

No bearer/share tokens, guest credentials, login cookies, or API tokens are added to snapshots. Typed drafts can contain sensitive gift text, item URLs, row versions, and purchase retry metadata; these remain protected in storage. Plaintext naturally exists in the active form and server circuit, so this is not a defense against a compromised active browser/page. Logout does not deliberately destroy an account's encrypted copies; they remain inaccessible to another account and can be recovered by the original account in that tab until expiry.

## Architecture and verification

The Razor `DraftRecovery<T>` component and tracking module belong to the reusable UI project. The encryption/browser adapter belongs to the web host. Another host, such as a future MAUI Hybrid app, must provide an appropriate account-bound, expiring `IDraftRecoveryStore` implementation. Hosts without that service do not offer recovery. No database migration, new endpoint, cloud resource, or tenant setting is introduced. The web circuit's incoming message limit is explicitly bounded to 256 KiB so the bounded encrypted/raw snapshots can round-trip without hitting the previous smaller default.

All 483 tests passed without skips, including SQL Server and headless Chromium. All nine unchanged coverage gates passed; Release builds completed with zero warnings/errors. Evidence is retained in `.artifacts/qol-draft-recovery-release/coverage.trx` and its coverage attachment.

Storage tests cover exact expiry, size/count limits, tampering, lost keys, form/account/tenant isolation, anonymous-to-account recovery, failed storage, and circuit identity changes. Component tests cover explicit restore/discard, schema failures, unsaved versions/raw fields, stale sessions, rejected targets, late callbacks, saving-state races, and initialization/interop failures. The real browser journey recovers every supported form, round-trips 4,000 non-ASCII characters, preserves a concurrent edit conflict, switches accounts without disclosure, rejects an archived item, and retries a committed purchase after a deliberately lost response without adding another mark. Restoration alone leaves business tables unchanged.

No real users, Azure resources, or hosted configuration were changed. The work is committed locally only; no push or deployment is included.
